The 60-second pitch

Lead with this. Have it memorised.

"I built a query engine for property graphs that implements a documented subset of ISO/IEC 39075:2024 — GQL, which became the international standard for graph query languages in 2024, the graph world's equivalent of SQL. It's not a Neo4j wrapper; the grammar, parser, planner and executor are all mine."

"It's structured like a compiler: a Lark LALR(1) grammar produces a typed AST, a schema-aware semantic pass rejects queries that are syntactically valid but meaningless against the ontology, a logical planner does predicate pushdown, and an executor streams binding rows. Separately I generate a normalised SQLite mirror of the same graph from the same schema file, so every benchmark query can be answered twice — once by my engine, once by SQLite — and compared."

"I validated it on a 712,000-node cricket knowledge graph built from Cricsheet ball-by-ball data, then refactored the whole thing to be domain-agnostic — you bring a JSON graph and a YAML ontology and it works on any domain. I proved that by running the same suite over movie, Star Wars and social-network graphs."

The line that lands

"The interesting result wasn't that graphs beat SQL — it's where each wins. Undirected neighbour lookup was 26× faster in my engine because the graph stores undirected adjacency natively while SQL needs a UNION ALL over both directions. But a bounded path query was hundreds of times slower, because I'm doing a raw BFS while SQLite has a B-tree index. Knowing which side of that line a workload falls on is the actual engineering judgement."

The storage layer, precisely

PropertyGraph keeps five dictionaries. Two are the primary stores (_nodes, _edges keyed by ID), two are adjacency lists (_out, _in — node ID → list of edge IDs), and two are label indexes (_by_label, _edge_by_label) so a labelled scan is O(matching) rather than O(all nodes).

Why both _out and _in: undirected traversal and reverse-direction patterns (<-[]-) need constant-time access to incoming edges. Without an in-index you'd scan every edge in the graph for each hop.

Idempotence is a design property, not an accident. add_node merges properties into an existing record rather than duplicating — but it raises if the label differs, because silently relabelling a node would corrupt every label index pointing at it. Same for edges: properties merge, but a changed label/src/dst raises. This is what lets you re-ingest the same source file twice and get a byte-identical graph, which the tests verify.

The query pipeline

Six stages. This is the centrepiece — be able to trace a query end to end.

Take this query and follow it all the way down:

MATCH (a:Person)-[:KNOWS*1..2]-(b:Person)
WHERE a.name = "Alice"
RETURN b.name AS reachable
1
Source text

input

A plain string. Nothing has been assumed about it yet.

2
Lark LALR(1) parse

query/grammar.lark → parser.py

The grammar file is the normative spec — that's a deliberate claim. Anything the grammar rejects is not in the language, so unsupported syntax fails loudly at parse time rather than being silently mis-parsed into a wrong answer.

LALR(1) not Earley: it's linear-time and it forces the grammar to be unambiguous. Both parsers are built once at import as module singletons — Lark's startup cost is the slow part, so you pay it once per process, not per query.

3
Transformer → typed AST

query/ast.py

A Lark Transformer collapses the parse tree into frozen dataclasses. Frozen means hashable and immutable — the AST can't be mutated by a later pass, so planner bugs can't corrupt the parse result. 

Query(
  patterns=(Pattern(
    nodes=(NodePat(var='a', label='Person', filters=()),
           NodePat(var='b', label='Person', filters=())),
    rels=(RelPat(var=None, label='KNOWS',
                 direction='undirected',
                 quantifier=('range', 1, 2)),)),),
  where=Comparison(lhs=Ref('a', 'name'), op='=', rhs='Alice'),
  projections=(Projection(expr=Ref('b', 'name'),
                          agg=None, alias='reachable'),),
  order_by=None, limit=None)
4
Semantic validation

query/semantic.py

The grammar proved syntax. This pass proves meaning against the ontology: variables must be bound, properties must exist on their label, edge labels must be real, endpoint labels must be compatible with the edge's declared direction.

Without a schema it degrades gracefully to structural checks only — the engine carries no embedded domain knowledge.

5
Logical planning

query/planner.py

The AST becomes a flat list of operators, and single-variable predicates get pushed down into the operator that produces that variable: 

ScanOp(var='a', label='Person',
       pushed=[a.name = "Alice"])   ← pushed out of WHERE

ExpandOp(from_var='a', edge_label='KNOWS',
         direction='undirected',
         quantifier=('range', 1, 2),
         to_var='b', to_label='Person')

ProjectOp(projections=(b.name AS reachable,))

Note there is no trailing FilterOp — the whole WHERE was absorbed. Instead of scanning every Person, expanding all of them, then discarding all but Alice, we filter Alice at the scan and expand exactly one node.

6
Execution

query/executor.py

Operators are Python generators chained together, each consuming and emitting binding rows — dicts mapping variable name → Node or Edge. Rows stream lazily through Scan → Expand → Filter; only ProjectOp materialises, because aggregation, ORDER BY and LIMIT all need the full set. 

# rows flowing between operators
{'a': Node(alice)}                    # after Scan
{'a': Node(alice), 'b': Node(bob)}     # after Expand
{'reachable': 'Bob'}                 # after Project

Why this shape matters

This is the textbook database architecture — parse, validate, plan, execute — and being able to name each stage and say what invariant it establishes is most of what a systems interviewer is checking for. The separation is real, not cosmetic: you can call parse() without a graph, validate_query() without executing, and plan() without data.

The grammar

gql_core/query/grammar.lark — 82 lines, the normative spec

query: match_clause where_clause? return_clause

match_clause: "MATCH" pattern ("," pattern)*
pattern:      node_pat (rel_pat node_pat)*
node_pat:     "(" CNAME (":" LABEL)? prop_filter_block? ")"

rel_pat: "-[" edge_var? edge_label? quantifier? "]->"  -> rel_out
       | "<-[" edge_var? edge_label? quantifier? "]-"  -> rel_in
       | "-[" edge_var? edge_label? quantifier? "]-"   -> rel_undirected

quantifier: "*"              -> q_star     # 1..∞
          | "+"              -> q_plus     # 1..∞
          | "*" INT          -> q_exactly  # exactly N
          | "*" INT ".." INT  -> q_range    # M..N

AGG.2: "COUNT" | "SUM" | "AVG" | "MIN" | "MAX"
LABEL: /[A-Z][a-zA-Z_0-9]*/

Two details worth pointing out unprompted

  • AGG.2 — the .2 is a terminal priority. Without it, COUNT would also match CNAME (a generic identifier) and the lexer would be ambiguous. Raising its priority forces the aggregate reading. That's a real lexer-conflict fix, not boilerplate.
  • LABEL requires an initial capital, which is what cleanly separates a label from a variable name in (p:Player) without needing lookahead.

The defensible position

Ten tests in test_regression.py assert that each unsupported keyword raises a parse error. The scope boundary is enforced by tests, so it can't silently drift. "It's a documented subset with a tested boundary" is a much stronger answer than "I didn't get to those."

RPQ traversal — the hardest part

Regular Path Queries. Expect to be pushed on this one.

A regular path query matches a variable-length path — "everyone within two hops of Alice". This is exactly what relational databases are bad at, and it's the reason graph query languages exist at all. Implementation is a BFS in rpq_traverse: 

queue = deque([(start, [])])
visited = {start.id}
if lo == 0:
    yield [], start          # *0..N: start matches at zero length
while queue:
    node, path = queue.popleft()
    depth = len(path)
    if depth >= hi: continue
    for edge, neighbor in _direct_neighbors(...):
        if neighbor.id in visited: continue
        visited.add(neighbor.id)
        if depth + 1 >= lo: yield path + [edge], neighbor
        if depth + 1 < hi:  queue.append((neighbor, path + [edge]))

Three semantic decisions to defend

1 — Binding-set semantics, not path semantics

The visited set is keyed by node ID alone, not (node, depth). So each reachable node is yielded exactly once, at its shortest depth. You get the set of reachable nodes, not the set of distinct paths.

This matches Cypher's binding-set semantics, and it's what makes the traversal terminate on cyclic graphs. A test drives an unbounded * over a deliberately cyclic undirected graph and asserts it terminates with exactly the right four nodes — that test exists because a naive implementation loops forever.

The trade-off to name out loud: you cannot ask "how many distinct paths reach this node", or find a longer path when a shorter one exists. If you needed path enumeration you'd key visited by (node, depth) and accept exponential blow-up on dense graphs.

2 — * means 1..∞, not 0..∞

Cypher's convention: bare * is shorthand for *1... Zero-length has to be asked for explicitly with *0..N, which yields the start node itself before the loop begins. Tests pin both: *0..3 returns exactly one more row than *1..3 — the start node.

3 — Multi-hop edge variables fail fast, on purpose

if len(edge_path) > 1:
    raise NotImplementedError(
        "Edge variable on a multi-hop RPQ pattern is not supported. "
        "Cypher binds a relationship list; this engine does not.")

In Cypher, -[e:KNOWS*1..3]- binds e to a list of relationships. This engine tracks a single edge. Rather than silently binding the last edge — which would make e.since quietly return the wrong value — it raises with an explanation.

This is the answer they want

"A wrong answer that looks right is worse than an error." That principle shows up three times in this codebase: here, in the semantic validator, and in the grammar's hard rejections. Being able to point at a consistent design philosophy across independent subsystems is a strong signal.

Planner & predicate pushdown

query/planner.py — four operators, one optimisation

ScanOp

Seed. Enumerates nodes by label (via the label index) applying inline filters and pushed predicates during the scan.

ExpandOp

Traverses one relationship pattern from an already-bound variable. Handles direction and quantifier.

JoinOp

Hash-join for multi-pattern queries. Joins on shared variables; Cartesian product when none are shared.

FilterOp / ProjectOp

Residual predicates, then projection, aggregation, ordering and limit.

The pushdown rule, and its deliberate limit

_split walks the WHERE tree. A Comparison referencing exactly one variable is appended to that variable's producing operator and removed from the residual. And nodes recurse into children, so each conjunct is considered independently. Everything else — Or, Not — is returned whole and lands in a trailing FilterOp.

Why OR is not pushed — and why that's correct

a.age > 30 OR b.city = "NYC" spans two variables. Pushing either half into one operator's scan would drop rows that satisfy only the other half. Disjunction can't be decomposed that way. A test named test_adversarial_or_predicate_not_pushed_but_correct exists precisely to prove the unpushed path still returns the right eight rows.

The other test worth mentioning: one test doesn't check the query result at all — it inspects the plan, asserting the v.city comparison actually landed in ExpandOp.pushed. That's testing the optimisation happened, not just that the answer was right. An optimisation with no test can silently stop firing.

Join strategy

For MATCH (a)-[]-(b), (a)-[]-(c) the planner emits ops for the first pattern, then a JoinOp carrying the second pattern's ops and the shared variables. At execution the right side is materialised into a hash index keyed by the shared variables' IDs, then the left side probes it. Standard hash join. With no shared variables it degrades to a Cartesian product — and a test asserts 16 × 5 = 80 rows for exactly that case, so the behaviour is pinned rather than accidental.

Semantic validation

query/semantic.py — the layer most people skip

This is the part of the project I'd lead with if asked "what shows the most judgement", because it's the layer a naive implementation omits entirely.

MATCH (p:Person) RETURN p.salary is syntactically perfect. Without a semantic pass it executes happily and returns [{'salary': None}] for every person — a wrong answer that looks like a real one. The user concludes everyone earns nothing. Here it raises: 

SemanticError: RETURN reference p.salary uses unknown
node property 'salary' on label 'Person'

Two subtleties that show care

  • Unknown node labels are tolerated; unknown edge labels are not. The docstring justifies the asymmetry: an unknown node label degrades to an empty scan, which is reasonable for exploration. An unknown edge label "almost always indicates a wrong translation" — so it errors. That distinction was reasoned about, not stumbled into.
  • Undirected endpoint checking accepts either orientation. For -[:KNOWS]- both (src, dst) and (dst, src) pass, because undirected patterns genuinely match both ways. Only directed patterns get the strict ordering check.
  • Graceful degradation. With no schema_path, only structural checks run (binding conflicts, unbound refs). The engine ships no embedded ontology, which is what makes it domain-agnostic.

Shapes & ingestion

validator.py + ingester.py — SHACL-inspired, YAML-declared

SHACL is the W3C Shapes Constraint Language — the RDF world's schema-validation standard. This borrows the idea (declare constraints per type, validate instances against them) in YAML rather than RDF triples. 

nodes:
  Person:
    required: [id, name]
    optional: [age, city]
    types: {id: str, name: str, age: int, city: str}
    enums: {role: [batter, bowler, allrounder]}
    patterns: {id: "^[a-f0-9]{8}$"}
    min: {age: 0}
    max: {age: 150}

edges:
  KNOWS:
    src: Person
    dst: Person
    undirected: true
    properties: {since: int}

Checks run in a fixed order — required → types → enums → patterns → bounds — and raise ShapeViolationError on the first failure, carrying the label, field, reason and offending value as structured attributes. Tests assert on exc.value.field and exc.value.reason, so error messages are part of the tested contract, not incidental strings.

The Python gotcha worth mentioning

if expected is int and isinstance(value, bool):
    return False

In Python bool subclasses int, so isinstance(True, int) is True. Without this guard, balls_per_over: true passes an integer type check and silently becomes 1. There's a dedicated test for it. It's a small thing, but noticing it is exactly the kind of detail an interviewer registers.

Ingestion

The wire format is gql-graph-json: @id, @type, @src, @dst are reserved; every other key becomes a property. Ingestion is two-pass — all nodes first, then all edges — because edge validation needs to look up both endpoints' labels to check them against the shape.

Edge IDs are optional and derived deterministically as {label}:{src}:{dst} when absent. That determinism is what makes re-ingestion idempotent: the same input yields the same IDs, and the store merges rather than duplicates.

The cricket domain layer (the original problem)

examples/cricket/ holds the domain-specific parser that turns Cricsheet ball-by-ball JSON into the graph: 7 node types, 9 edge types. Two bits are worth describing:

  • Derived edges. TEAMMATES_WITH doesn't exist in the source data — it's materialised by taking combinations(players, 2) per match and incrementing a match_count. Undirected edges are stored canonically with src = min(id), dst = max(id), so the pair (Babar, Rizwan) and (Rizwan, Babar) are the same row. That canonical form is exactly why the SQL translation needs a UNION ALL — and why the graph is 26× faster on that query.
  • Deterministic IDs. ids.py is pure functions, no I/O. delivery_id is match:innings:over.ball; venue is slug(venue)@slug(city) with an unknown@unknown fallback. A fixture exists specifically to exercise that fallback.

The SQLite mirror

mirror.py — schema-driven, zero domain knowledge

To compare a graph engine against SQL you need the same data in both. build_mirror generates a normalised relational schema from shapes.yaml alone:

  • One table per node label, one per edge label. PascalCase → snake_case.
  • Type map: str→TEXT, int→INTEGER, float→REAL, bool→INTEGER, list/dict→TEXT as JSON.
  • id always becomes TEXT PRIMARY KEY.
  • Every edge table gets indexes on both src and dst automatically, plus any composite filter_indexes declared in the shape.

Why the indexes matter for honesty

Indexing every join column means SQLite's query planner gets a fair shot. Benchmarking your own engine against a deliberately unindexed baseline is the classic way to produce a flattering, worthless number. Explicitly indexing the competitor is the credible move — and it's why the RPQ result is unflattering to the graph engine.

Two oracles, and the reason both are needed

This is the single best thing to say about the project. The code itself carries the caveat:

Quoted from the harness metadata

"SQLite parity validates executor agreement with a mirror derived from the graph; independent fixture gold tests are required to catch shared ingestion or modeling errors."

The logic: the SQLite mirror is built from the same ingested graph. So if ingestion has a bug — say it drops every third delivery — both engines see the same wrong data and parity passes. Cross-engine agreement can only detect disagreement, never a shared upstream fault.

That's why hand-computed fixture answers are a separate, independent track. The fixtures are five tiny synthetic matches, small enough that every expected value (Babar's 31 runs, 7.75 average, 11 highest score) is computable by hand. As the regression suite's docstring puts it: two engines can share a bug, but they can't both independently produce the exact same hand-computed number.

Row comparison

Both sides are canonicalised before comparison, which handles four real problems:

  • Graph rows are dicts, SQL rows are tuples → both become tuples.
  • Row order is not guaranteed → deterministic sort, with None forced last so "missing" and "null" compare consistently.
  • Column aliases may differ between the two queries → extract by key_columns when all are present, fall back to positional (dict insertion order = RETURN order).
  • Floats → math.isclose(rel_tol=1e-6), applied only when either side is a float, so averages don't produce spurious failures.

Timing decomposition

Every query is timed in three scopes: full pipeline (parse + validate + plan + execute), parse/plan only, and execute only on a pre-built plan. That attribution is what lets you say "the RPQ cost is traversal, not parsing" with evidence — Q5 is 382 ms end to end but under a millisecond of it is parsing. Measurement is timeit.repeat with warm-up, reporting median and p95 rather than mean, so a single GC pause doesn't dominate.

The NL→GQL track

A separate benchmark translates 100 natural-language questions into GQL with a local LLM (Ollama, temperature=0.0 for reproducibility), then executes the generated query and compares its rows against a hidden SQL oracle. Three things make it credible:

  • Correctness is judged on result rows, never textual similarity to a reference query. Two very different queries that return the same answer both count as correct.
  • The SQL oracle is never shown to the model.
  • Parse errors feed back into the prompt for a bounded retry — grammar-guided repair rather than hoping the model gets it right first time.

How to narrate this table

Q4 — the graph wins, 26×. Undirected adjacency is native to the graph: one index lookup. In SQL, TEAMMATES_WITH is stored canonically (one row per pair, a < b), so finding all of Babar's partners needs a UNION ALL over both directions. The data model, not the engine, is doing the work.

Q5 — SQL wins, catastrophically. A bounded path walk over 703,000 NEXT_DELIVERY edges. My engine does a raw BFS in Python; SQLite runs a recursive CTE against a B-tree index. This is the honest counter-example, and volunteering it is worth more than hiding it.

LR2 — the expressiveness claim, quantified. The same question takes 7.2× more SQL tokens than GQL, and the SQL requires WITH RECURSIVE plus CASE expressions to unwrap the canonical undirected storage. Runtime is comparable (2.3 vs 1.9 ms) — so the argument for graph query languages here is developer expressiveness, not speed. Saying that distinction out loud is the mature framing.

The four testing strategies, named

  1. Hand-computed oracles. Fixtures are deliberately tiny so every expected value is verifiable by inspection. This is the only oracle that catches bugs shared by both engines.
  2. Cross-engine parity. Graph executor vs SQLite mirror on canonical row sets — a semantic-drift detector across all Q, LR and NL queries.
  3. Documented-limitation-as-test. Unsupported syntax must raise; multi-hop edge variables must raise NotImplementedError; unknown properties must raise SemanticError. These tests pin the boundary of the language so it can't silently drift.
  4. Structural invariants. Assertions that hold regardless of data: undirected edges are symmetric including match_count; *0..3 returns exactly one more row than *1..3; *1..5 never exceeds 5 hops.

Three tests worth describing by name

  • Cyclic unbounded Kleene terminates. Runs TEAMMATES_WITH* over a cyclic undirected graph and asserts termination with an exact four-node result. Without the visited set this hangs forever.
  • Empty-result aggregation semantics. Two paired tests pin that COUNT with no group key returns [{n: 0}], but with a group key returns []. Genuinely ambiguous behaviour, resolved deliberately and locked down.
  • AND/OR precedence. A AND B OR C and (A OR C) AND B must produce different results — a classic boolean-evaluation bug caught by construction.

Known limitations — say these before they find them

Verified during this review. Owning them reads as senior; being caught doesn't.

Bug 1 · README's own example doesn't run

# README, Python API section:
run_query("... WHERE n.name = 'Alice' ...", graph, ...)
UnexpectedCharacters: No terminal matches "'"

The grammar imports Lark's ESCAPED_STRING, which is double-quote only. Cypher and GQL both accept single quotes. One-line fix: add a single-quoted string terminal. Say it as: "The grammar only accepts double-quoted strings — the standard allows both. I found it re-reading my own README, which is a good argument for testing your documentation examples."

Bug 2 · Unbounded accumulator in the mirror builder

rows = []
for node in graph.nodes_by_label(label):
    row = []                        # ← declared, never used
    for col in col_names:
        rows.append(val)            # ← appends to the OUTER list
    cur.execute(sql, tuple(rows[-len(col_names):]))   # ← slices the tail

Functionally correct — the tail slice always grabs the right values — but rows grows for the entire table instead of being reset per node. On 712 K nodes that retains millions of values for no reason, and row is dead code. Both point at the same typo. Output verified correct; it's a memory and clarity bug, not a correctness one.

Structural · The refactor is incomplete

There are two parallel code trees: the original cricket-specific query/, graph/, ingestion/, and the generic gql_core/. ast.py and grammar.lark are byte-identical duplicates; semantic.py differs by 508 lines. The test suite imports from both, and pyproject.toml still ships all of them.

Frame it as sequencing: "I extracted the generic engine and ported the tests incrementally so I always had a green suite. The legacy tree is still there because the cricket benchmarks import it. Deleting it is the next commit — and I'd do it by moving those benchmarks onto the generic engine first, not by deleting and fixing fallout."

Smaller items

  • Dead branch in _resolve_param: if order == "first" and the fallback return the identical expression.
  • No lazy projection — ProjectOp materialises all rows. Necessary for aggregation and sorting, but a LIMIT without ORDER BY could short-circuit and doesn't.
  • No cost-based planning. The seed is always the first node in the pattern, not the most selective one. A real planner would use label cardinality to pick the smallest scan.
  • No property-based or fuzz testing. Grammar surface is enumerated by hand; random query generation is the obvious next step.
  • Performance is measured, never asserted. No test fails on a latency regression.
  • The two stacks have no cross-parity test — a semantic divergence between legacy and generic engines would go undetected.
  • social.db is committed — a generated artifact in version control.

Likely questions

Rehearse the first four out loud.

Why build this instead of using Neo4j?

"Neo4j would have been the right call to ship a product. The goal here was to understand the layer Neo4j hides — how a graph query language is actually specified and executed. GQL became an ISO standard in 2024 and there are very few open implementations, so implementing the grammar was a way to read the standard properly rather than skim it. The benchmark harness came out of that too: once I had my own executor I could measure it against SQL on identical data and find out where the graph model genuinely pays off."

Your RPQ is much slower than SQL. Why?

"Because I'm doing an uninstrumented BFS in Python over 703,000 edges, and SQLite is running a recursive CTE against a B-tree index. It's the expected result and I published it rather than dropping the query."

"Three things would close the gap: the traversal is pure Python object-chasing, so a compact adjacency representation like CSR arrays would cut the constant factor dramatically; I have no cardinality statistics, so I always seed from the first node in the pattern rather than the most selective one; and I don't push the target-side filter into the traversal, so I expand nodes I'll immediately discard. The first is the biggest win."

How do you know your engine is actually correct?

"Two independent oracles, deliberately, because either alone is insufficient. Cross-engine parity against a SQLite mirror catches executor bugs. But the mirror is built from the same ingested graph — so if ingestion has a bug, both sides see the same wrong data and parity passes silently."

"That's why the second track exists: hand-computed answers over five tiny synthetic fixtures where every value is verifiable by inspection. Two engines can share a bug; they can't both independently produce the same hand-computed number. That caveat is written into the harness metadata, not just something I say in interviews."

What was the hardest bug?

"Kleene-star semantics. The first version keyed the visited set by (node, depth), which seemed more general — but on a cyclic graph like TEAMMATES_WITH it produced duplicate rows and, unbounded, never terminated."

"Fixing it forced me to decide what a variable-length pattern actually means: the set of reachable nodes, or the set of distinct paths? I chose reachability — visited keyed by node ID alone, each node yielded once at its shortest depth — because that matches Cypher's binding-set semantics and guarantees termination. It's a real expressiveness trade-off: I can't answer 'how many distinct paths reach this node'. The regression suite has a test that runs unbounded * over a cyclic graph specifically to keep that fixed."

Why a formal grammar instead of regex or hand-rolled parsing?

"Three reasons. The grammar file is the specification — 82 lines that unambiguously define the language, which is much easier to review than parsing logic scattered through a hand-written recursive-descent parser. LALR(1) forces the grammar to be unambiguous, so ambiguities surface as build-time conflicts rather than runtime surprises. And unsupported syntax fails at parse time with a precise error and column number instead of being silently mis-parsed."

"I did hit a real lexer conflict: COUNT matched both the aggregate terminal and the generic identifier rule. Lark solves that with terminal priority — AGG.2. That's the kind of thing a hand-rolled parser hides in special-case branches."

How would you scale this past memory?

"Right now everything is in one process's heap — 712 K nodes fits, tens of millions wouldn't. I'd go in three steps rather than jumping to a distributed store."

"First, change the representation: replace the dict-of-objects adjacency with CSR-style arrays — sorted integer node IDs, an offsets array, a neighbours array. That alone cuts memory several-fold and makes traversal cache-friendly, which is also the RPQ fix. Second, make the graph memory-mappable so the OS page cache handles working-set management instead of loading everything eagerly. Only then would I consider partitioning, and I'd want the query mix first — partitioning a graph badly makes traversal dramatically worse, because every cross-partition hop becomes a network call."

Walk me through what happens when I run a query.

Use the six stages from section 3, and trace the example query concretely. The single most impressive beat is stage 5 — pointing out that WHERE a.name = "Alice" gets absorbed into the ScanOp, so the plan has no filter operator at all and the expansion runs from exactly one node instead of every Person in the graph.

What would you do differently?

"I'd build it domain-agnostic from day one. I wrote the cricket engine first and generalised second, which left me maintaining two parallel trees — that's the biggest piece of debt in the repo right now."

"I'd also add cardinality statistics to the planner earlier. Predicate pushdown was the easy optimisation; choosing the seed node by selectivity is the one that actually matters for multi-pattern queries, and retrofitting statistics into a planner that assumes first-node-wins is more invasive than designing for it."
